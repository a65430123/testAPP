# 壓力測試

腳本在 `server/scripts/loadtest.ts`：模擬大量玩家同時登入、進入地圖、走動、聊天、到野外打怪，量測伺服器的反應時間與穩定度，最後給出通過或未通過的判定。

## 執行方式

測試帳號是**真的寫進資料庫**的帳號（`load_00000`、`load_00001`…，會重複使用），請只對測試環境執行，不要對正式環境跑。

1. 啟動伺服器，並把登入頻率限制調高（否則同一個 IP 的大量登入會被擋下）：

```bash
AUTH_RATE_LIMIT=100000 npm run server
```

2. 另一個終端機執行壓測：

```bash
BOTS=200 DURATION_SEC=120 npm run loadtest
```

| 環境變數 | 說明 | 預設 |
|---|---|---|
| `SERVER_URL` | 伺服器位址 | `http://localhost:2567` |
| `BOTS` | 模擬玩家數 | `50` |
| `DURATION_SEC` | 全部上線後持續多久 | `60` |
| `RAMP_SEC` | 用多久讓所有玩家陸續上線 | `20` |
| `FIELD_RATIO` | 多少比例去野外打怪（其餘留在城裡走動） | `0.5` |
| `PREFIX` | 測試帳號的前綴 | `load` |

**要測得準，壓測程式要跑在另一台機器上**，並透過與玩家相同的路徑連線（經過 Nginx 與 HTTPS）。在同一台機器上跑，壓測程式會跟伺服器搶 CPU，也測不到網路與反向代理的影響。

## 模擬玩家做什麼

- 登入（沒有帳號就註冊）、取得角色（沒有就建立，六個職業輪流）。
- 加入角色所在地圖的房間；同一張地圖超過 80 人會自動分流到新的房間。
- 每 1–3 秒做一件事：
  - 城裡的玩家：在附近隨機挑一個可以走的格子移動。
  - 野外的玩家：走到傳送點進入嫩芽草原，攻擊最近的魔物，打倒後換下一隻；倒地會被送回城，再走回去。
  - 3% 的機率在地圖頻道說一句話。
- 被斷線會在 2 秒後重新連線（模擬玩家重新整理）。

## 報告怎麼讀

| 項目 | 意義 | 通過門檻 |
|---|---|---|
| 登入＋取得角色 | HTTP API 的回應時間；主要花在密碼雜湊上 | 失敗率 ≤ 1% |
| 加入房間 | 驗證憑證、從資料庫載入角色、建立連線 | 失敗率 ≤ 1% |
| 移動反應時間 | 送出移動要求到自己的位置開始變化；玩家感受到的「點了多久才動」 | 95% ≤ 250 毫秒 |
| 狀態同步間隔 | 相鄰兩次同步的間隔；伺服器設定是 50 毫秒 | 95% ≤ 150 毫秒 |
| 伺服器事件迴圈延遲 | 伺服器忙不過來的直接指標（由 `/api/health` 回報） | 最大 ≤ 200 毫秒 |
| 非預期斷線 | 被伺服器或網路中斷的次數 | 0 |
| 壓測程式自身延遲 | 壓測這台機器是否忙不過來；偏高時其他數字會失真 | 僅供參考 |

門檻是「玩家不會感覺到卡」的經驗值，寫在腳本最後面，可以依需求調整。任何一項不符，腳本會以非零狀態結束並列出原因。

`/api/health` 也可以單獨拿來做監控：

```bash
curl http://localhost:2567/api/health
```

回傳線上人數、運作時間，以及最近 10 秒事件迴圈延遲的平均與最大值。

## 本機實測結果（僅供參考）

2026 年 11 月在開發用的容器裡測的：4 核心、伺服器與壓測程式與 PostgreSQL 都在同一台、走 localhost、bcrypt 成本設為 10。**這不是正式環境的容量數字**，只能說明程式本身在這個量級沒有明顯的瓶頸。

| 模擬玩家 | 加入房間（中位數／95%） | 移動反應（中位數／95%） | 同步間隔 95% | 伺服器迴圈延遲最大 | 斷線 | 判定 |
|---|---|---|---|---|---|---|
| 200 | 9／20 毫秒 | 75／99 毫秒 | 53 毫秒 | 20 毫秒 | 0 | 通過 |
| 500 | 10／25 毫秒 | 67／93 毫秒 | 56 毫秒 | 11 毫秒 | 0 | 通過 |
| 1000 | 42／472 毫秒 | 103／199 毫秒 | 136 毫秒 | 11 毫秒 | 0 | 通過 |

觀察：

- 1000 人時伺服器的事件迴圈延遲仍然很低，但用戶端量到的數字變差，同時壓測程式自身的延遲升到 139 毫秒——**這一組的瓶頸有一部分在壓測程式本身**，要換到另一台機器才能判斷伺服器真正的上限。
- 測試只用到兩張地圖。每張地圖 80 人一個房間，1000 人大約是十幾個房間。
- 測試中發現並修掉一個問題：房間超過 10 個時，Node 會對房間之間的訊息轉送印出「監聽器過多」的警告。

沒有測到的：

- 真實網路延遲與封包遺失、經過 Nginx 與 TLS 的負擔。
- 更長的時間（記憶體是否緩慢成長）。建議正式壓測至少跑 2 小時。
- 交易、商店、精煉、倉庫、組隊、公會、任務等操作（模擬玩家只會走路、聊天、打怪）。
- 大量玩家擠在同一個房間的同一個畫面（每個房間上限 80 人）。
- 資料庫在另一台機器時的延遲；連線池目前上限是 10 條。

## 正式壓測的建議流程

1. 準備與正式環境相同規格的測試機與資料庫，壓測程式放在另一台。
2. 先跑預期同時在線人數的 1 倍，確認通過。
3. 逐步加到 2 倍、3 倍，找出第一個不通過的指標，那就是容量上限；開服的人數上限設在它的一半左右。
4. 用預期人數跑 2 小時以上，期間觀察：
   - 伺服器行程的記憶體是否持續上升。
   - PostgreSQL 的連線數、慢查詢、磁碟寫入量（`item_log` 成長速度）。
   - 伺服器日誌中的錯誤與「存檔失敗」訊息。
5. 壓測進行中對伺服器送 SIGTERM，確認所有線上角色都有存檔、重啟後位置正確。
6. 壓測進行中重啟資料庫，確認伺服器不會當掉、資料庫恢復後存檔會重試成功。
7. 把結果（人數、各項指標、機器規格）記在這份文件裡，之後每次大改版重跑比較。

## 找到瓶頸之後

| 症狀 | 可能原因 | 方向 |
|---|---|---|
| 伺服器迴圈延遲升高 | 單一行程的 CPU 用滿（Node 是單執行緒） | 多開幾個行程分擔房間（需要先把線上名冊、隊伍、訊息轉送改用 Redis） |
| 登入很慢、其他正常 | 密碼雜湊佔用 CPU | 調整 bcrypt 成本，或把雜湊移到工作執行緒 |
| 加入房間很慢 | 載入角色的資料庫查詢 | 檢查索引與連線池上限 |
| 同步間隔變長但迴圈延遲正常 | 頻寬或用戶端處理不來 | 縮小同步範圍（只同步視野內的玩家與魔物） |
| 存檔失敗、資料庫連線逾時 | 連線池用完或資料庫負載高 | 加大連線池、降低定時存檔的頻率、把紀錄表移到獨立磁碟 |
